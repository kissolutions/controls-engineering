# PROC-CTL-M1-SCOPE — v0.1 (proposed)

**Purpose:** establish contractual and project evidence sources; extract obligations and responsibility boundaries before detailed controls design. Applies in Phase 1 and whenever documents/revisions change.

**Inputs:** authorized project storage; contract/project schedule and scope documents, plans/specifications, addenda and RFIs; vendor documentation; internal current and historical PM/PE tracker information; existing markups; source revisions.

**Method**

1. Declare authoritative storage/registers for this project. Register each source (ID, filename, type, issue/revision/date, exact locator, origin and relevant authority). Separate contract source, vendor/product evidence, field observation, internal engineering decision and prior-work observation.
2. Extract atomic scope statements: *what*, *where/system/equipment*, *responsible party*, *work action* (furnish, install, remove, reconnect, rewire, modify, program, integrate, monitor, test, document), *deliverable*, *source locator*, and known exclusions/conditions.
3. Identify System of Interest, external and internal boundary/interface candidates. Use `in_scope`, `interface_only`, `adjacent_context`, `excluded` or `unresolved` independently of whether an object is physically shown on a drawing.
4. Compare text, plans, schedules, contractual responsibility divisions, approved equipment submittals and existing project workbook rows. Product capability is different from contract responsibility. Conflicts get both source citations and an open item; no automatic universal precedence.
5. Preserve pre-existing engineering work as separately attributed prior work, neither discarded nor silently elevated to primary source authority.
6. Have an independent pass enumerate and compare scope obligations/exclusions from the registered source set. Report omissions, unsupported claims, contradictory scope and unresolved responsibility boundaries.
7. Generate derived Scope Navigator/Scope Infographic and a concise discrepancy report from the authoritative register. Mark the presentation's source/revision, review scope, unknowns and review state.

**Work products:** source/revision matrix; scope/responsibility/action register; interface list; source discrepancies, open items/RFIs; scope review package. All have declared authoritative or derived roles.

**Completion:** every identified source and consequential scope obligation accounted for; independent scope coverage review performed; unresolved boundaries assigned accountable owner, priority and `resolve_by` gate; human acceptance of the *M1 review scope* recorded. Acceptance of M1 does not imply every individual proposed configuration is accepted.

**Limits:** no live SharePoint/Drive link is a substitute for authorized file contents; no scope entry is auto-approved solely because it appears in a contractor's preliminary takeoff. Incomplete source access is a documented limitation, not permission to fill gaps.

**Process evidence:** process revision; source/register input revisions; project/scope; output register/review package revisions; reviewer/findings/disposition; approved tailoring.
