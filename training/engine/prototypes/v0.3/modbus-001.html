01.1 · Academic learning · Protocol architecture

Modbus fundamentals

Modbus describes the request and response. RS-485 or Ethernet carries that message. A gateway bridges those two worlds, but it does not magically increase serial bandwidth.

Build the mental model

In conventional Modbus RTU, one serial master initiates requests, and a addressed slave responds. The segment has no token passing or native discovery. Each individually addressed slave normally uses an address from 1–247; address 0 is reserved for broadcast commands that do not elicit a response.

From BACnet MS/TP: both may use RS-485 wiring, but MS/TP uses a token for bus access among masters. Modbus RTU generally relies on a single coordinated master. Identical cable does not imply identical protocol behavior.

Explore the communication path

Change the architecture. The diagram retains the same conceptual devices while showing who communicates over TCP versus RTU.

What travels in a request?

RTU frameAddress · Function · Data · CRC

Serial framing and CRC validation; timing depends on baud and format.

TCP application frameMBAP · Function · Data

MBAP contains the Unit ID. No RTU CRC is carried inside the TCP application data unit.

Diagnose by layer

Ping succeeds: gateway IP is reachable. TCP 502 opens: a TCP service is reachable. Valid Modbus response: an endpoint processed the request. Only a valid end-to-end response or meaningful downstream evidence demonstrates the target RTU transaction actually worked.

Engineering trap: 247 usable addresses do not establish 247 electrically allowable devices, 247 gateway routes, or acceptable polling performance.

Sources: Modbus RTU reference · Modbus TCP reference.

01.2 · Academic learning · Physical layer

RS-485 physical networks

RS-485 is a shared differential electrical interface. A valid Modbus configuration cannot compensate for a broken conductor, excessive common-mode voltage, or an unsuitable topology.

Walk a trunk in physical order

Document the gateway port, the cable route, first and last sensors, taps, junctions, power supplies and possible isolation boundaries. Slave IDs do not describe physical cable order. RS-485 sensor nodes do not relay or regenerate downstream messages.

The field sequence

  1. Measure sensor supply voltage at the near, middle, and far devices under normal load.
  2. Verify A/B polarity using both manufacturers' documentation; the labels themselves are inconsistent across suppliers.
  3. Confirm termination only at the two electrical ends of a supported linear bus.
  4. Check biasing/fail-safe receiver behavior, signal reference, shielding, grounding and galvanic isolation.
  5. Verify transceiver unit loads, cable specifications, stubs, topology and gateway-specific device limits independently.

What does the ohmmeter actually prove?

With the network properly de-energized and measurements made only where safe and appropriate, two isolated 120 Ω terminations in parallel have an equivalent resistance near 60 Ω. The reading can be influenced by connected circuitry and does not prove resistor placement or waveform integrity.

Safety: never resistance-test an energized trunk. Do not change grounds, disconnect active controls, or isolate sections without an approved operating plan. Restore proper termination/bias when temporarily shortening a test segment.

01.3 · Academic learning · Data model

Registers & addressing

A correct request requires the right slave/Unit ID, function code, starting address and quantity. A successful transaction can still yield a nonsensical engineering value if decoding is wrong.

FC03Holding registers

Read 16-bit holding-register values. Conventional display labels start with 4xxxx.

FC04Input registers

Read 16-bit input-register values. Conventional display labels start with 3xxxx.

Try the address translator

For the traditional five-digit 4xxxx display convention, the displayed holding register 40001 corresponds to transmitted starting offset 0. Some vendors and drivers use one-based fields instead: verify the actual manual.

Zero-based protocol starting offset10040101 → offset 100

Five checks before calling the data wrong

  1. Slave ID or gateway Unit ID and serial port route.
  2. Function code and register table (FC03 versus FC04).
  3. Starting offset convention and requested register quantity.
  4. Signedness, 16/32-bit width, and byte/word ordering.
  5. Scale, engineering units, and manufacturer model/firmware revision.
Example: a two-register 32-bit vibration reading needs not just the correct starting offset, but the documented word order and scaling. Modbus does not standardize how a particular manufacturer encodes that measurement.

01.4 · Academic learning · Translation and routing

TCP-to-RTU gateways

A gateway is an interface between communications domains. One Ethernet connection can access many downstream addresses, but those serial requests still share limited RTU airtime.

Trace a request end to end

  1. The BAS or PLC TCP client opens the configured gateway IP and Modbus TCP port (commonly 502).
  2. The Modbus TCP MBAP header carries a Unit Identifier; the gateway uses its configuration to identify the target serial route.
  3. The gateway forwards/translates the request onto the selected RTU port with the proper RTU framing.
  4. The addressed sensor returns an RTU response; the gateway presents the corresponding Modbus TCP response to the client.
Two downstream ports do not automatically make duplicate slave IDs unambiguous through a single gateway IP/port. Confirm the manufacturer's exact routing modes and how they distinguish ports.

Ask the manufacturer about client limits, request queuing, port-specific loading, retries and how requests are distributed among serial ports. A gateway accepting more TCP clients does not make the RTU segment faster.

01.5 · Academic learning · Capacity and timing

Polling & fault budgets

Protocol addressing, electrical unit loads, and the gateway's supported routes are separate constraints. Polling throughput is a fourth constraint: can the network meet its required scan interval?

A healthy FC03/FC04 transaction

For a read of R 16-bit registers, a normal RTU request is 8 bytes and a normal response is 5 + 2R bytes. Approximate serial wire time:

wire_time = (13 + 2 × R) × bits_per_character / baud

Then add measured/estimated device response, required silent gaps, and any gateway turnaround not already counted.

Worked example · 30 hypothetical sensors

Each device returns 10 registers using FC03 at 19,200 baud, 8E1 (11 bits/character), 20 ms device turnaround, 5 ms additional allowance, and a five-second target scan.

Nominal single transaction43.9 ms18.9 ms on wire + 25 ms allowance
Thirty-sensor scan1.32 s26.3% of the five-second budget

What if sensors stop responding?

At 500 ms timeout and two additional retries, an offline device may consume about 1.5 seconds instead of 43.9 ms. Three such failures can push the estimated full cycle to approximately 5.69 seconds—past the target.

Healthy utilization below 100% is not a guarantee of acceptable performance. Other TCP clients, queueing, failure retries and vendor timing rules can consume the remaining budget.
